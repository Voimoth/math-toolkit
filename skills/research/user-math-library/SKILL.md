# 用户数学资料库整理(/mnt/e/书籍)

管理用户(中科大中法班数学系大二)的本地数学资料库 `/mnt/e/书籍/`。目标:保持分类体系稳定,新增资料必须**并入既有结构**。

## 触发条件

- 用户要求整理/归档书籍、PDF、讲义
- 新增外部分享包(如 pika)需要并入资料库
- 用户问"XX 资料应该放在哪"
- 用户提到"分类""整理""并入""重复""查重"等词

- 用户问纸质书/实体书怎么转电子档、要不要买扫描仪（走 `references/paper-to-digital.md`）

## 铁律(用户明确纠正过,务必遵守)

> **用户原话:"整合进我原有的分类体系,而不是直接新建文件夹"**

1. **禁止新建顶层文件夹**(/mnt/e/书籍 下只应有:分析、代数、数学专业书籍、数学学习方法、物理)。
2. **分类逻辑**:
   - 与**当前课程强相关** → `/mnt/e/书籍/分析/` 或 `/mnt/e/书籍/代数/`(课程讲义按 分析I/II/III、代数I/II 分子目录)
   - **其余所有材料** → `/mnt/e/书籍/数学专业书籍/` 下按学科子目录
   - **数学学习方法类**(学习方法/自学指南/解题技巧/思维洞察/数学家访谈)→ `/mnt/e/书籍/数学学习方法/`
   - **教材型的数学史与「高观点」书**（Klein《高观点下的初等数学》、Stillwell《Mathematics and Its History》）→ `数学专业书籍/新增杂项/`，**不要**塞进 `数学学习方法/05_数学家访谈与历史`：那里是访谈与通俗文章，教材混进去会降低该目录的可检索性。
3. **移动而非复制**(省空间);完成后删除临时容器文件夹。
4. 大规模移动前先向用户确认关键决策点;用户信任时可按映射表直接执行并给完整报告。
5. 用户明确说"删掉就好"(如近世代数 5 本书与体系不相容)时,可直接删除该文件夹。
6. **顶层目录同时就是检索权重,别随手挪。** `bookdex` 按根目录定层级:只有 `分析/代数/物理/数学学习方法`
   四个顶层算 tier 3(课程在用),`数学专业书籍` 是 tier 1;路径里带 `MPSI` 的提到 tier 2。
   所以把课程书挪进 `数学专业书籍/` 等于给它降权,反过来乱加顶层文件夹会让噪声书浮上来。
   挪完跑一次 bookdex 增量索引,并用 `select tier,count(*) from books group by tier` 核一下分布。

## 整理工作流

1. **先看结构**:列出 /mnt/e/书籍 顶层 + 目标学科目录现状,确认既有分类。`~/下载` 的批量批次先逐个 `pdfinfo`(页数/生成日期) + `pdftotext -l 1 -layout` 首屏再分类:正课讲义(有目录/章节号)/习题课讲义(编号习题)/作业(单页几题)/TD(法语)——同一批里这几类去向不同目录,不先判就会归错。
2. **制定映射表**:新资料每个子目录 → 对应学科目录(参考 references/library-mapping.md)
3. **关键决策点先确认**(若拿不准):并入既有目录 vs 新建子目录、课程相关判定、散乱文件归属
4. **执行**:`mv -n`(先确认目标不存在);跨盘移动会先复制再删源,大文件先 `du` 核对大小再删源
5. **验证 + 报告**:文件数、大小、最终结构
6. **归档完把目录索引补上**:`~/.local/share/bookdex/venv/bin/python ~/.local/share/bookdex/index.py`(增量,只处理新增/改动文件)。
   `bookdex` 是全库「书名 + 书签目录」索引,不跑它,刚归进来的新书在「哪本书讲过 X」的查询里是**隐形**的——
   会给用户「书库里没这个」这种反向错误结论。同理,大删/改名之后也要跑一次让存量同步。
   - **法文资料归档后核一眼 OCR 语种**：bookdex 扫描件按语种选 tesseract 语言包（法文走 `fra+eng`），
     判错的记录 `dir_src` 会是 `ocr:eng`；要重刷必须先 `update books set dir_src='' where path like …`
     再跑增量——增量只处理 `dir_src=''` 的书，直接重跑不会动它。刷完抽查带重音的法文词
     （théorème / Algèbre / polynôme）能命中才算对。
   - **改 bookdex 的 index.py/query.py 前先确认没有后台增量在跑**：长跑会被切成后台进程并持有旧版模块，
     跑完会把旧逻辑的结果写回去（语种标签、dir_text 都可能被覆盖，而且从标签上不易察觉）。
     改前 `ps aux | grep '[i]ndex.py'`，改后核一遍 `select dir_src,count(*) from books group by dir_src`，
     并逐条对一下 `ocr:*` 标签是否与当前 `ocr_lang(path)` 一致。

## 查重工作流(重复文件清理)

用户会要求清理重复书籍。**精确查重必须用哈希,不能用文件名/大小判断**:

1. **先按文件大小分组**(`Group-Object Length`),只对同大小的组算哈希——大库(1万+文件)直接全量哈希太慢
2. **哈希用系统 `md5sum`(秒级完成万级文件)**;需要结构化报告时用 Node 脚本(`scripts/find_duplicates.js`,本机 node 在 `~/.hermes/tools/`)。脚本见 `scripts/find_duplicates.js`(只读,生成报告)和 `scripts/gen_delete_list.js`(生成"保留/删除"清单,不实际删除)
3. **同名文件组**≈重复(验证 MD5 一致后确认);同大小但不同名的也需要 MD5
4. **保留策略**:每组按路径排序保留第一个(通常是主分类目录),删除副本
5. **删除前必须向用户确认**:列出删除文件数+总大小+典型示例,并指出特殊类型(如"长期更新.几千T资源大合集"这类出现在 14 个目录的资源索引 .doc——问用户是否全删)。不可直接批量删除大量文件
6. **执行删除**用 `scripts/delete_duplicates.js`(读清单 → 删"删除:"行 → 保护名单防误删临时文件 → 记日志)。2026-08 实测:13,762 文件扫出 3,485 个重复,删除 0 失败,释放 ~55GB
7. 完成后删除临时脚本(_find_dups.js 等)和报告文件

### 查重陷阱(2026-08 实测)

- **MD5 足够,不要再用 SHA256 全量复核**:MD5 碰撞在正常文件场景下不可能出现(文件都来自正常渠道)。本会话曾对 11,000+ 文件跑 SHA256 复核,15+ 分钟未完成,被判定为过度谨慎后终止——直接信任 MD5 清单即可
- **大文件组是大头**:几百 MB 的 PDF 哈希很慢,按大小分组后大文件组的哈希占绝大多数时间;可接受等待或按需分批
- **临时脚本文件要防误删**:查重脚本自身、报告文件、bat 脚本都在 PROTECT 名单里,否则可能被自己的删除流程删掉
- 大规模删除后**抽查验证**:取 2-3 个之前重复的书名,确认现在只剩 1 份
