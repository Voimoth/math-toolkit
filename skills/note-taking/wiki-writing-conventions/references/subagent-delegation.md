# 子代理分工（vault 维护场景）

用户明确要求把“多借助子代理、省上下文”写成规则（原话：「这种重复工作你扔给子代理就好，直接跑浪费上下文」）。vault 是单个 git 仓库 + 单个库，所以分工按「文件清单切分 + 父代理独占 git」来做，而不是一律只读。

## 何时派

- ≥ 5 个文件的机械改动（批量替换、批量规范化、批量核查）
- 跨课程/整库调查（记号统计、断链排查、内容覆盖对照）
- 独立评审（大编辑门槛里的无上下文评审）
- 批量转写的分段并行（整门课入库，见 `math-notes-transcription`）

低于这个量自己做完更快——写 prompt + 汇总结果的开销比直接干大。

## 硬规则

1. **分两类，别一律只读**。调查/评审类：子代理**只读**，不动 vault。批量规范化类（缩写展开、记号迁移、格式统一）：可以**直接改**，但必须满足三条 —— 按文件清单切分且**互不重叠**（每个子代理只拿自己的清单，在自己的文件里写）、子代理**禁一切 git 操作**、父代理统一复核后一次性 commit。实测 133 文件 / 5 并行写未出冲突；真正的风险不是并发写，而是子代理之间**口径不一致**（见第 5 条）。
2. **报告落盘到 cache**：`~/.hermes/cache/<任务名>/`，不要写进 vault（vault 自包含，临时产物不入库）。
3. **交付机器可读**：TSV/JSON（`file, line, before, after` 或 `结论 + 证据`），不要散文报告。
4. **规则只给路径，不给正文**：每个子代理拿到的是同一份规范文件的绝对路径（如 `references/notation-rules.json`），不要把规则抄进 prompt——多份副本一定会漂。
5. **主代理核数 + 收口**：用自己的脚本/grep 统计与子代理自报对账；抽样 10% 复核，且抽样必含最长/最复杂的行。子代理说“已全部完成”不算证据。**批量规范化任务必须额外做一遍“口径收口”**：不同子代理会对同一决策点给出不同答案（中文笔记到底用「定义」还是 Définition、v.a. 单复数、标签语言），父代理要用同一个判据重新扫一遍全部文件，不能拿汇总表直接提交。
6. **并发上限 5**：vault 在 USB NTFS 上，IO 是瓶颈；本项目实测 5 个起草任务并行正常，再多只是排队。
7. **小批合并**：每批完成即复核、入库、commit，不做最后一次性合并——一次性合并的 diff 无法复核，出错也无法定位到批次。

## 起草类任务的交付

- 子代理只回**清单**（文件名、字节数、出链列表、两行摘要），正文留在文件里，不要回灌进对话。
- 起草前必须让它读：规范文件 + 相邻页样本 2 篇；否则文风与 callout 用法会跑偏。
- 父代理逐页读开头、定义、出链，再跑链接/记号/emoji 检查，最后才落盘。
- **让它顺手当审稿人**：prompt 里明确要求「若源笔记与证明/后续命题矛盾，按数学判对错并在清单里报出」，不要照抄。实测这一步能抓出源笔记的真错（生成元写反、pgcd/ppcm、命题与证明矛盾）；父代理拿清单逐条复核后改源笔记，改法见 SKILL 正文「源笔记可能有数学错误」。
- **判重后不要直接删草稿**：草稿与已有概念页同题（典型：不同课程各有一页）时，先把草稿里已有页没有的段落并进那唯一一页（并补一条互链），再删草稿；直接删会把子代理重写出来的内容丢掉。
- **允许它交“超长”的判断**：起草页超出字数上限时要它说明超的是哪节、删了会不会伤主链，父代理再定拆或留；不要求硬塞进限额。

## 典型任务拆分

- 记号迁移：按课程拆，每节课一个子代理（概念页 + 笔记分开更好），输出改写清单；主代理按单课落盘 + commit。
- 概念页补页：一页一个子代理，输入是“对应笔记章节 + 概念页规范 + 现有相邻页 2 篇”，输出是页草稿写到 cache；主代理逐页核语义、链、回链后落盘。
- 全库调查：按目录拆，输出统计表；主代理汇总并抽查原始行。
- 批量文字规范化（缩写展开、标签语言统一、交换图环境替换）：先脚本统计出受影响文件清单 → 按目录/文件数切成 `/tmp/<任务>/T1.txt…` → 每个子代理读同一份规则文件 + 自己的清单，改完自己跑 `check_notation.py --check` 与 `check_formulas.js`（公式 0 失败）→ 父代理用同一判据收口一遍 → 一次性 commit。规则文件写“判据 + 映射表 + 例外”，不写具体文件内容。
